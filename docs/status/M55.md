# M55 — Hosted runtime: one container for API, worker and web

Status: **implemented and verified in a local container against a local nearcore sandbox; not deployed to any
host** (deploying is the owner's step: [runbook](../runbooks/hosted-deploy.md)). No testnet or mainnet transaction
was sent in this module, no account was created, nothing was published. The escrow contract and the deployment
`gnanam1990-dock-escrow2.testnet` (code hash `7GEti5E6NWcjq8kHj5Gweed5HwggY1cxPD7cfbB65h8N`) are unchanged.
Decision record: [ADR-0027](../adr/0027-hosted-runtime-container.md). Branch `feat/dockside-m55-hosted-runtime`.

## What was built

| Piece | Where | What it does |
|---|---|---|
| Image | `Dockerfile`, `.dockerignore` | Node.js 22 image pinned by digest; builds the workspace with the usual commands and keeps production dependencies, compiled packages, migrations, the isolated signer script and the web build. No key, no seed, no sources, no development tools inside (checked by the verification). |
| Entrypoint | `deploy/entrypoint.sh` | the only code that runs as root: makes the volume writable for the `dockside` user (uid 10001), copies the relayer function-call key from the host's secret (a mounted file or `RELAYER_KEY_JSON_B64`) into an owner-only file outside the volume, removes the variable, drops privileges for good |
| Launcher | `services/hosted/src/{main,profile}.ts` | turns the host's environment into the M43 testnet profile, creates the service key seeds on first start with the existing custody tools, starts the unchanged API and worker on loopback, opens the public port only when both are ready, ends the container with a child's exit status (78 for a refusal) |
| Front | `services/hosted/src/front.ts` | the one public HTTP listener: the web build with the same CSP and security headers as the preview server (plus HSTS), `/v1`, `/healthz`, `/readyz` to the API, `/relay` to the worker's relay; decides nothing itself |
| Demo seed | `services/hosted/src/{seed,seed-cli,demo-policy}.ts` | `seed-demo enroll | grant | status`: three demo organisations, the `commercial-docs` evidence policy, both service identities with proof of possession, one invitation per trade role, all through the real API with signed challenges and request proofs; people accept invitations with their own device keys |
| Host configurations | `render.yaml`, `fly.toml`, `deploy/escrow-manifest.json` | one instance, persistent disk at `/data`, health check `/readyz`, HTTPS by the host, the testnet escrow, relayer account and RPC; the key only as a host secret |
| Guide | `docs/runbooks/hosted-deploy.md` | ten steps from the local proof to a trade on the hosted app, with the refusal table |
| Verification | `scripts/hosted/verify-container.mjs` (`pnpm run hosted:verify`) | builds the image and runs it against a local nearcore sandbox prepared like testnet |

Configuration the operator supplies: `DOCKSIDE_ESCROW_CONTRACT_ID`, `DOCKSIDE_NEAR_RPC_URL`,
`DOCKSIDE_RELAYER_ACCOUNT_ID` (all three are in `render.yaml` and `fly.toml`), the relayer key secret, and
optionally `DOCKSIDE_ORIGIN` (otherwise taken from the host) and limits. Paths and loopback ports are owned by the
launcher and refused when set by hand.

What `hosted:verify` proves, in a real container against a real nearcore node running the reproducible wasm:

- the image builds from the Dockerfile and contains no key, seed, `.env`, source tree or development tool;
- **fail closed:** without a relayer key the container exits 78 (`RELAYER_SIGNER_NOT_PROVISIONED`); with the
  relayer's full-access key it exits 78 (`FULL_ACCESS_KEY`); in both cases the public port never opens;
- with the function-call key it starts: the API passes the chain preflight (code hash equals the manifest), the
  worker's custody checks pass on chain, three service keys are created on the volume;
- from outside the container: `/healthz` 200, `/readyz` ready with `near-testnet` and funded payouts `BLOCKED`,
  the web app with the strict CSP, every script and stylesheet it names, an application route, the relay status,
  the relay's refusal of a `fund` deposit, a 401 for an unauthenticated API call;
- every Node.js process runs as uid 10001; the relayer key is a `0600` copy outside the volume; no log line
  contains it;
- the demo seed creates three organisations, the policy, two ACTIVE services and four invitations; a second run
  creates nothing and shows no secret; a person outside the container accepts an invitation with their own key
  through the public port, `seed-demo grant` grants the role, and that person's session then carries
  `BUYER_APPROVER`;
- `docker stop` exits 0; a new container on the same volume, with the key now supplied as the secret variable,
  finds the same keys, database, organisations and the person's still-valid session, and no process has the
  secret variable in its environment.

## Real, simulated, pending

| | State |
|---|---|
| Image, entrypoint, launcher, front, seed | **real**: exercised in a container and over HTTP |
| Chain in the verification | **local nearcore sandbox** (real node, real transactions, the reproducible escrow wasm); not testnet |
| Default profile against NEAR testnet | **read-only preflight only** (code hash and chain id checked from the image); no transaction |
| Render or Fly.io deployment | **pending, owner**: `render.yaml` and `fly.toml` are checked against the code by tests but were not applied to a host here; host-specific behaviour (secret prompts, disk ownership, health-check timing) is unconfirmed until the first deploy |
| A full trade on the hosted app | **pending, owner and friends** (the same product path passes in the browser against the sandbox in M43) |
| INV-13 acceptance | **not claimed**: the seed's three administrators are one operator; trade roles are held by the people who accept invitations |

Known limits: all visitors share the unauthenticated rate-limit budget (the API sees the front's loopback address;
forwarded headers are not trusted); one instance only (SQLite on one volume); the host's secret store can read the
relayer function-call key; a volume snapshot contains the service key seeds; `hosted:verify` is not part of CI (it
needs Docker and `.data/repro`).
