- Decision record: [ADR-0028](../adr/0028-supplier-cash-out-through-1click.md). It goes beyond the sealed

## What it does

On the trade's Payout tab, section "7. Move to another chain", shown with controls only to the trade's supplier
signer:

1. **Destination and amount.** The supplier picks the token to send (a NEP-141 token on NEAR that 1Click
   lists), the amount, the destination chain and token, a destination address and a slippage tolerance.
2. **Dry quote.** The API asks 1Click for a `dry: true` quote and shows amount out, guaranteed minimum, the
   cost of the route (fee), the destination withdrawal fee, the estimated time and the deadline. Nothing is
   committed: no deposit address exists afterwards.
3. **Real quote from the supplier's own client.** The panel shows the same request with `dry: false` (refund
   to the supplier's own NEAR account) as JSON, as a PowerShell command and as a curl command. The supplier
   runs it and pastes 1Click's answer.
4. **Deposit from the supplier's own wallet.** After checking the pasted answer field by field and against
   1Click itself, the panel shows one exact `ft_transfer` and the near-cli-rs command for the supplier's
   keychain, the same pattern as the funding panel. Dockside sends nothing; the escrow and the relayer are
   not involved.
5. **Tracking with reconciliation.** Each status read combines 1Click `/v0/status` with two NEAR reads (the
   transaction the supplier names and the token balance of the deposit address). A deposit call is offered
   again only when the chain proves the earlier attempt moved nothing. A missing or unclear answer is
   `UNKNOWN` and says "Do not send the deposit again".

| State | Meaning | Deposit may be sent |
|---|---|---|
| `AWAITING_DEPOSIT` | 1Click waits, nothing sent, deposit address empty, quote open | yes, once |
| `DEPOSIT_FAILED_NO_TRANSFER` | the named transaction is the quoted transfer, final and failed; address empty; quote open | yes |
| `DEPOSIT_SENT_WAITING_FOR_PROVIDER` | the transfer is final on NEAR, or the address already holds the token; 1Click not yet | no |
| `IN_PROGRESS` | 1Click `KNOWN_DEPOSIT_TX` or `PROCESSING` | no |
| `DELIVERED` / `REFUNDED` / `FAILED` | 1Click `SUCCESS` / `REFUNDED` / `FAILED` | no |
| `INCOMPLETE_DEPOSIT` | 1Click received less than quoted | no |
| `QUOTE_EXPIRED` | less than one minute left before the deposit cut-off | no |
| `UNKNOWN` | 1Click or NEAR unreadable, unknown deposit address or transaction hash, a different transaction, still executing | no |

The tests were written with the code they cover. Two of the guards were then weakened on purpose to see the
tests fail and restored: sending the caller's `dry` flag instead of `true` fails "the client cannot be made to
send dry:false", and ignoring the deposit address balance fails the reconciliation route test.

What the tests show, in the order a cash-out happens:

- The server's only quote request carries `dry: true`; the simulator holds no deposit address after it.
- Only the supplier signer reaches any route (buyer, inspector, risk, supplier administrators: 403; another
  organisation: 404; no session: 401).
- A pasted answer for another recipient, another refund account, another amount, a swapped or invented deposit
  address, an expired quote or a quote already past `PENDING_DEPOSIT` gives no deposit call.
- If 1Click is silent, errors or answers in another shape, a dry quote is an upstream error, a deposit call is
  not handed out, and tracking says `UNKNOWN` with no call.
- A failed deposit transaction (the token refused it) allows one more attempt; once the deposit is on chain,
  the answer is "do not send again" with the right hash, with the old failed hash and with no hash.
- Exactly one transfer of the exact amount left the supplier's simulated account.

### Not verified against the real service

These come from the published API description and are untested here until the owner's dry quote and optional
real run:

- that the real dry answer decodes with the strict decoder (if it does not, the panel reports an upstream
  error and shows no quote; the evidence script prints the reason);
- that 1Click accepts a `.testnet` refund account in a dry quote (relevant only to the preview on a testnet
  deployment);
- that a 1Click deposit address on NEAR is registered with the token contract before the deposit (if it is
  not, the `ft_transfer` fails on chain, nothing moves, and tracking reports `DEPOSIT_FAILED_NO_TRANSFER`);
- that the fee without a partner token equals what the supplier's own unauthenticated request gets. The
  figures the supplier is bound by are the ones in their own real quote, which the deposit panel shows.

### Network limit today

The public 1Click service settles on NEAR mainnet and this build's configuration still refuses
`DOCKSIDE_NETWORK=near-mainnet`. On a testnet deployment pointed at the public service the panel is therefore a
**preview**: dry quotes work, the deposit step is not offered and the panel says why. The deposit step turns on
without further code when a trade's network equals the 1Click network.

## Owner steps

```powershell
# 1. One real dry quote as evidence (no deposit address, nothing moves). Replace the two values.
pnpm run build; node scripts/one-click/dry-quote-evidence.mjs --refund-to YOUR-ACCOUNT.near --recipient 0xYOUR-ARBITRUM-ADDRESS

# 2. Show the panel on a deployment (preview on testnet): add to the API environment and restart.
$env:DOCKSIDE_ONE_CLICK_URL = "https://1click.chaindefuser.com"
```

If you have a 1Click partner token, save it in a file outside the repository and set
`DOCKSIDE_ONE_CLICK_TOKEN_FILE` to that file's path before either step.

On the hosted container (M55) the same variable is passed through: add `DOCKSIDE_ONE_CLICK_URL` to the host's
environment settings. It is not set in `render.yaml` or `fly.toml`, so a hosted deployment does not call
1Click until the owner turns it on.

Not run for this module: `pnpm run test:sandbox`, `pnpm run web:e2e:sandbox` and `pnpm run hosted:verify`
(local nearcore and container suites). The change adds routes and an optional configuration block and does
not touch the paths they cover.

## README snippet

```markdown
### Move a payout to another chain (NEAR Intents)

After a release the money is in the supplier's own NEAR account. On the trade's **Payout** tab the supplier
can move it to another chain through NEAR Intents 1Click:

1. Choose the destination chain, token and address, and the amount.
2. Dockside asks 1Click for a `dry: true` quote and shows the amount out, the fee and the deadline. Nothing is
   committed.
3. The supplier requests the real quote from their own client (the exact request is shown) and signs one
   `ft_transfer` from their own wallet. The escrow and the relayer never touch this money, and Dockside holds
   no key that could.
4. Dockside tracks the cash-out from 1Click's status and from NEAR. If an answer is missing or unclear the
   state is UNKNOWN and the deposit is never offered again blindly.

Status: tested against a local 1Click simulator and a simulated chain. 1Click runs on mainnet only, so on the
testnet deployment the panel is a preview (dry quotes). Enable it with `DOCKSIDE_ONE_CLICK_URL`. Details:
[docs/status/M52.md](docs/status/M52.md), [ADR-0028](docs/adr/0028-supplier-cash-out-through-1click.md).
```
