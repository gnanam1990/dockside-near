## Stranded trade `trd_9aced7e741a0462ac88ef4de0e67ba81`

On chain: funded 0.05 NEAR by `gnanam1990-dock-buyer.testnet`, all of it reserved by release intent
`rli_7781d4f0bb0b6aa6461935a154614c02` in `VALUE_LOCKED`, no approval, no attempt, blocker `APPROVAL_MISSING`,
conservation `true`. The expired `approve_release` was therefore never included.

Every exit for this value needs a Dockside principal signature: an approval, a dual-signed CANCEL, an ABANDON by the
designated buyer approver or supplier signer after the intent's expiry plus one day, and every refund row
(`TRADE_EXPIRY` and `MUTUAL_CANCEL` also require that no release intent holds value). The journey derives those
principal keys from a random seed that run-all never stores (by design, so that run-all holds no key material). The
seed of run 2 is gone, so **nobody can sign for this trade any more, and its 0.05 testnet NEAR stays locked in the
escrow**. It is testnet NEAR with no value, and the contract's conservation still holds. A refund on testnet
(USER-NEXT-STEPS §7.8) therefore needs a new trade whose principals are enrolled people or services with kept keys.

## Findings and fixes (run-all on Windows)

| # | What happened | Fix (test first: `packages/near/test/m24-run-all-windows.test.ts`) |
|---|---|---|
| F1 | near-cli-rs 0.31.1 asks "Which signature scheme should the new key pair use?" in `account add-key … autogenerate-new-keypair`; run-all redirected its output to `relayer-key.txt`, so the question was invisible and step 5 appeared to hang. Closing stdin is not enough on Windows: near-cli-rs's terminal library reads the console itself and waited with stdin from `/dev/null` (observed here with `near account view-account-summary </dev/null`, stopped after 120 s) | `--signature-scheme ed25519` (the exact 0.31.1 option, from `near account add-key … autogenerate-new-keypair --help`, and the command near-cli-rs itself printed for re-running). Every near-cli-rs command now runs through `tool.mjs near-run` (or the journey's runner) with stdin closed and `</dev/null` in the script; the runner stops near-cli-rs as soon as it draws a question (`◆ … ?` or its key-help line) and fails with `stopped at "<question>"`, which the real near-cli-rs on this host now does in 0.15 s. A total timeout (`DOCKSIDE_NEAR_CLI_TIMEOUT_MS`, default 300 s) ends any other hang; a timeout is never retried |
| F2 | The Node helpers spawn near-cli-rs without a shell; on Windows npm installs only `near`, `near.cmd` and `near.ps1` shims, so the journey failed `ENOENT` (`NEAR_CLI_MISSING`) | `resolveNearCli` in `lib/near-tools.mjs`, used by `tool.mjs near-cli` (the shell script takes its `NEAR_BIN` from it) and so by every near-cli-rs call: NEAR_CLI wins when it names a binary; on Windows a shim (in NEAR_CLI or from `where near`) maps to `node_modules/near-cli-rs/node_modules/.bin_real/near.exe` beside it, and without NEAR_CLI the npm global prefixes (`npm_config_prefix`, Node's directory, `%APPDATA%\npm`) are searched first; off Windows the default stays `near`. On this host it resolves the npm-installed near.exe (`near-cli-rs 0.31.1`) |
| F3 | `approve_release` failed with near-cli-rs "Error: Transaction has expired." (the RPC's `InvalidTxError::Expired`: rejected before inclusion) and run-all reported only "printed no transaction id" | `classifyNearFailure`: only `EXPIRED` is retried, by running near-cli-rs again (a fresh nonce and block hash, i.e. fresh signing), at most 3 attempts with 2 s and 4 s pauses. A printed transaction id, a timeout, an unavailable RPC, a prompt or any other error is never retried. Every failure message now carries near-cli-rs's own error lines (`describeNearFailure`), and `near-run` writes every attempt's output to the record file. Optional fallback RPC URLs (`--fallback-rpc-urls`, `DOCKSIDE_FALLBACK_RPC_URLS`), validated like `--rpc-url` (https, not mainnet; loopback for sandbox), serve the read-only checks when the primary fails at transport level; an RPC answer is final. near-cli-rs submits through its own `testnet` connection |

Also: the key-file and transaction-id parsers take the last match, so a record file holding a retried attempt yields
the successful one. `scripts/testnet-deploy/README.md` has Windows notes (near.cmd interactively, PowerShell
execution policy, the one-line command).
