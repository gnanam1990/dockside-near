## What the sandbox tests prove (real nearcore, real transactions)

- **T-045**: the deployed code hash (`view_account`) is base58(sha256) of the container-built wasm and
  equals the build manifest's `nearCodeHash`; `new` refuses `near-mainnet` and any other label, and a
  second `new` is refused.
- **T-007 / T-019 / T-022**: register (returned digest equals the core's), deposits below the minimum
  and to unknown trades refused, 3 + 2 NEAR from two funders, 1 NEAR excess QUARANTINED, attestation,
  forged inspector key refused, inspection PASS, intent locks exactly 5 NEAR, duplicate intent joins,
  execution refused before approval (`APPROVAL_MISSING`), approval, execution: the supplier's balance
  rises by exactly 5 NEAR, `PAID`, per-funder `released`, conservation; a forged private callback and a
  second execution are refused; attached value on a non-payable method is refused.
- **T-008 / T-009**: excess return requestable only by the original funder's own transaction, 1-hour
  cooling on chain time, the funder receives exactly the excess; MUTUAL_CANCEL needs the initiator's
  signature and the supplier's cosignature over the same digest (a wrong key is refused), then the buyer
  receives exactly its own 3 NEAR; both refunds `REFUNDED`, conservation.
- **T-020 / T-021 / T-042**: a forged proposal is refused, a unilateral proposal cannot activate, early
  activation is `DELAY_NOT_ELAPSED`, after the signed delay the revision is 2 with the new destination;
  the old intent and manifest no longer count (`INVALID_STATE`, `MANIFEST_NOT_CURRENT`); after new
  evidence and approval the alternate destination receives exactly 5 NEAR and the old one nothing.
- **T-031**: a release to a valid but non-existent account is refunded by the runtime; the settlement
  callback records FAILED and the exact reservation returns to `available`.
- **T-051**: a real NEP-141 `ft_transfer_call` is recorded and kept, never credited (native ledger
  unchanged); only the sender's own transaction may request recovery; risk approval; execution refused
  before 72 hours of chain time and without the 1-yoctoNEAR adapter deposit; then the token contract
  returns the exact amount to the sender and the asset is `RECOVERED`.

After every accepted call the harness compares `get_ledger`, `get_refunds` and `get_unexpected_asset`
with the core replay at the receipt's block time (deposit times included), and every refusal carries the
same failure code on chain and in the core.
