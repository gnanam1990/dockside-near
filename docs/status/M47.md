## The six refusals

One trade (default 0.05 NEAR), the hold journey with the amount paid in two deposits. Each refused call is built so
that exactly one thing is wrong with it.

| # | Call | What is wrong, and only that | Sent by | Must fail with |
|---|---|---|---|---|
| 1 | `fund`, half the trade amount attached | the deposit names the digest of the same terms with the payout moved to the relayer account, not the registered revision's digest | the buyer's own account | `STALE_REVISION` |
| 2 | `request_refund` `PARTIAL_FUNDING_RETURN` | the request is the one the funder could send from its own account at that moment (its whole PARTIAL value); the relayer sends it | relayer key | `FORBIDDEN` |
| 3 | `submit_inspection` | the inspection attestation the contract has just accepted, byte for byte | relayer key | `NONCE_REPLAYED` |
| 4 | `create_release_intent` | signed with the bound buyer key, but the destination is the relayer account, not the supplier the terms bind | relayer key | `DESTINATION_MISMATCH` |
| 5 | `execute_release` of the real intent | the deterministic-policy hold is ACTIVE | relayer key | `HOLD_ACTIVE` |
| 6 | `approve_release` | the approval the buyer would sign at that moment, signed with a key the terms do not bind | relayer key | `SIGNATURE_INVALID` |

On chain, in order (17 transactions: 11 accepted, 6 refused): `register_trade`, `register_evidence_policy`, **1**,
`fund` (first half), **2**, `fund` (second half), `submit_manifest_attestation`, `submit_inspection`, **3**,
`set_hold`, **4**, `create_release_intent`, **5**, `resolve_hold`, **6**, `approve_release`, `execute_release` → PAID.

Honest limits of the six:

- Refusal 5: when the release is attempted there is no approval yet either. The contract reports every blocker and
  takes the first as the code: the panic text is `DOCKSIDE:HOLD_ACTIVE: release conjunction incomplete:
  HOLD_ACTIVE,APPROVAL_MISSING`. An approval cannot be recorded first, because the contract refuses to approve while a
  hold is active (also `HOLD_ACTIVE`), so the hold cannot be isolated from the missing approval on one intent.
- Refusal 2 uses `PARTIAL_FUNDING_RETURN`, not `EXCESS_FUNDING_RETURN`: both are funder-only rows with the same caller
  check, and the partial row needs no excess left quarantined in the escrow after the run. The host test also shows
  the same request is accepted from the funder's own account, so the refusal is about the caller alone.
- All keys of the trade derive from one operator's seed, as in the other run-all journeys. The journey is evidence
  about the deployed contract. It is not acceptance by separate people (INV-13), and it does not go through the API
  or the web app.

## What run-all checks for every refused call

1. Before sending: the core (the journey mirror, on a copy of its state) must refuse the call with the expected
   code. If it would accept it or answer another code, nothing is sent (`REFUSAL_NOT_EXPECTED`).
2. The transaction is sent with near-cli-rs like every other call (the buyer's keychain key for `fund`, the relayer's
   function-call key file otherwise). near-cli-rs 0.31.1 exits 1 for a failed transaction and prints its id.
3. From the RPC (`EXPERIMENTAL_tx_status`, `FINAL`): the one receipt on the escrow is a `Failure` whose panic text is
   `DOCKSIDE:<expected code>: …`. A success stops the run with `REFUSAL_ACCEPTED`, another code with
   `REFUSAL_MISMATCH`. The core, given the same call at that receipt's block time, must answer with the same code and
   the same message (`MIRROR_MISMATCH` otherwise).
4. `get_trade`, `get_ledger`, `get_refunds`, `get_evidence`, `get_holds` and `get_release` are read before and after
   the call and must be identical, and must equal the core's views of a state that never saw the call
   (`REFUSAL_CHANGED_STATE` if neither holds; both held for every refusal in the sandbox runs).
5. `journey.json` records the transaction hash, block hash and time, expected and actual code, the full panic text
   and the signer's balance before and after; `run-record.json` marks the transaction `refused: <CODE>`.

Final checks (`journey.checks`): `allRefusedWithExpectedCode` (six, in order, right method and code),
`refusalsChangedNothing`, `refusedDepositReturned` (the buyer lost less than the deposit attached to refusal 1: the
runtime returned it), `relayerReceivedNothing` (the account refusals 1 and 4 tried to pay), the supplier's balance up
by exactly the trade amount over the whole run, the buyer's ledger funded = released = the trade amount, and the hold
journey's checks (`holdWasActive`, `releaseBlockedByHold`, `holdResolved`, `settledTrue`, `releasePaid`,
`supplierReceivedExactAmount`, `ledgerConservation`).

`--stop-after` counts refused transactions; `--resume` settles a refused call that was in flight from the chain (it
must be that call, failed, with the expected code) and never sends it twice.

## Validation

### near-sandbox (real transactions, deployable wasm)

`contract/integration/sandbox-tests/tests/run_all_on_sandbox.rs`,
`run_all_refusal_journey_six_calls_are_rejected_on_chain_and_the_trade_is_then_paid`, run by
`pnpm run contract:sandbox` on its own node and four fresh accounts:

- one `run-all --network sandbox --journey refusal` deploys the wasm, adds the relayer's function-call key and runs
  the journey: `run-all: PASS: … refusal journey six calls REFUSED, then PAID`;
- the test then reads all 17 transactions back from the node itself (`EXPERIMENTAL_tx_status` through curl, not
  run-all's reader): signer, receiver, method; the 11 accepted ones have no failure; the 6 refused ones are failed
  transactions whose escrow receipt panicked with `Smart contract panicked: DOCKSIDE:<expected code>: …`;
- from the transactions' own arguments: refusal 1 attached exactly half the amount and named another digest than the
  two accepted deposits, whose digest is the registered revision's; refusal 2 names the buyer as funder, reason
  `PARTIAL_FUNDING_RETURN`, half the amount, and was signed by the relayer; refusal 3 carries the same argument bytes
  as the accepted inspection; refusal 4 names the relayer as destination and the accepted intent the supplier;
  refusal 5 carries the same arguments as the `execute_release` that later pays; refusal 6 approves the same intent as
  the accepted approval with another signature;
- afterwards on the node: supplier balance up by exactly the trade amount; relayer balance lower than at the start;
  the buyer spent the trade amount plus fees and less than amount plus the refused deposit; ledger funded = released
  = the amount, every other bucket 0, conservation true; `get_refunds` empty; `get_release` PAID and no intent naming
  the relayer; one hold, RESOLVED;
- an amount whose half is below the minimum deposit is refused before any call (exit 2, no trade registered);
- a second refusal journey on the same deployment is stopped after five transactions (`--stop-after 5`: paused with
  the trade half funded, seed file mode 0600) and finished with `--resume`: all six refused, PAID.

The records of the first journey of that run are in [`docs/evidence/M47/`](../evidence/M47/). Their transaction hashes
belong to a throwaway local node and cannot be looked up anywhere; they show the shape of the record the testnet run
will produce.

## Owner run on testnet

Checked read-only on 2026-11-13 through `https://test.rpc.fastnear.com` (no transaction): escrow2 runs
`7GEti5E6NWcjq8kHj5Gweed5HwggY1cxPD7cfbB65h8N`; `get_config` minimum deposit 0.001 NEAR, 3 trades; buyer 9.798 NEAR;
relayer function-call key `4X66…QaZf` restricted to escrow2 with 0.988 NEAR allowance left (the journey needs 14
relayed calls of at most 0.01 NEAR each); testnet gas price 100000000.

From the repository root in PowerShell, with `.data/repro/dockside_escrow.wasm` and `.data/repro/build-manifest.json`
in place (the files the earlier runs used). `<relayer key file>` is the key file argument of the hold and refund
commands in `scripts/testnet-deploy/README.md`:

```powershell
$env:DOCKSIDE_ESCROW_ACCOUNT="gnanam1990-dock-escrow2.testnet"; $env:DOCKSIDE_BUYER_ACCOUNT="gnanam1990-dock-buyer.testnet"; $env:DOCKSIDE_SUPPLIER_ACCOUNT="gnanam1990-dock-supplier.testnet"; $env:DOCKSIDE_RELAYER_ACCOUNT="gnanam1990-dock-relayer.testnet"; powershell -ExecutionPolicy Bypass -File .\scripts\testnet-deploy\run-all.ps1 --network testnet --rpc-url https://test.rpc.fastnear.com --skip-deploy --relayer-key-file "<relayer key file>" --journey refusal
```

It takes about two minutes, costs the buyer 0.05 testnet NEAR (paid to the supplier) plus fees, and ends with
`run-all: PASS: … refusal journey six calls REFUSED, then PAID` and exit 0. Keep `run-record.json` and `journey.json`
from the run directory it prints (not `journey-seed.json`). If it stops part way, run the same four variables with
`run-all.ps1 --resume <run dir>`; near-cli-rs prints `Transaction failed` in red for the six refused calls, which is
the expected outcome.

After the run, any of the six transactions can be checked by anyone (replace the hash and the signer: the buyer for
the refused `fund`, the relayer for the others); the answer must contain `"Failure"` and `DOCKSIDE:<CODE>`:

```powershell
curl.exe -s https://test.rpc.fastnear.com -H "content-type: application/json" -d '{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"EXPERIMENTAL_tx_status\",\"params\":{\"tx_hash\":\"<hash>\",\"sender_account_id\":\"gnanam1990-dock-relayer.testnet\",\"wait_until\":\"FINAL\"}}'
```

## README snippet (for the later integration stage; README.md is not edited here)

```markdown
### Refusal journey: six calls the contract rejects, then the trade completes

One command sends six calls that must not work, each as a real transaction, and the escrow fails every one with a
named error before the same trade is paid normally:

| Attempt | The contract answers |
|---|---|
| Fund the trade while naming different terms (a wrong terms digest) | `STALE_REVISION` |
| The relayer asks for a refund only the original funder may request | `FORBIDDEN` |
| Replay an inspection the contract already accepted (same nonce) | `NONCE_REPLAYED` |
| A buyer-signed release intent that pays an account the terms do not bind | `DESTINATION_MISMATCH` |
| Release while a policy hold is active | `HOLD_ACTIVE` |
| An approval signed by a key the terms do not bind | `SIGNATURE_INVALID` |

After each refusal run-all reads the failed transaction back from the RPC, requires the exact error code, and checks
that the trade, ledger, refunds, evidence, holds and release views are byte-identical to before. The deposit attached
to the refused funding call returns to the buyer, nothing reaches the account the redirected calls named, and the
supplier is then paid exactly the trade amount.

    scripts/testnet-deploy/run-all --network testnet --skip-deploy --relayer-key-file <key file> --journey refusal

Validated with real transactions on a local nearcore node against the deployed wasm
(`7GEti5E6NWcjq8kHj5Gweed5HwggY1cxPD7cfbB65h8N`); details and the testnet transaction hashes are in
[docs/status/M47.md](docs/status/M47.md).
```
