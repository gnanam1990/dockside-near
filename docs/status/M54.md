## What it does

| Piece | Where | What it does |
|---|---|---|
| Receipt page | `site/proof/receipt.html`, `site/proof/receipt.mjs` | Printable receipt: parties, amount, asset, inspection result, release intent, release transaction (explorer link), escrow and its code hash, and a QR code of the receipt's own address with the verified transaction pinned in it. A green or red verdict and every check with expected and actual value. "Print receipt" and "Verify again". |
| Receipt verifier | `site/proof/lib/receipt.mjs` | Read-only, in the reader's browser, at one final block: code hash equals the proof manifest; trade registered on that network; inspection PASS and not invalidated; a PAID release intent; its approval names this inspection and evidence manifest; conservation recomputed from `get_ledger` and the contract's flag; released total equals the paid intents; the transaction is a final, successful `execute_release` of this trade and intent; the escrow's only transfer in it paid exactly the intent's amount to its destination. Unreadable is ERROR, never a pass. |
| QR encoder | `site/proof/lib/qr.mjs` | ISO/IEC 18004 model 2, byte mode, all versions and levels, deterministic. Used by the page and by the PDF. |
| Signed receipt | `GET /v1/trades/:id/payment-receipt` (`services/api/src/receipt.ts`) | For the buyer, the supplier and members of their organisations (others: "not found"). Reads the contract afresh and the journal's release operation; refuses unless the release is PAID with a recorded transaction. Signs the statement with the audit-export key under the new domain `dockside/payment-receipt`; audited `PAYMENT_RECEIPT_SIGNED`. |
| PDF | same file | One page, PDF 1.4, deterministic: the receipt as text, the QR code, the signature block, and the signed statement attached as `dockside-receipt.json`. |
| Offline verifier | `pnpm run verify-receipt <pdf> --trusted-keys <keys.json>` (`services/api/src/cli/verify-receipt.ts`) | Header, attachment, schema and fields, digest, Ed25519 signature, key trusted / origin / not revoked / validity window (shared with `verify-export`), and a byte-for-byte re-render of the PDF from the signed statement. Exit 0 / 1 / 2. |
| Web app | payout tab, "Payment receipt" | "Prepare signed receipt": the browser re-checks digest, signature, key and that the PDF carries exactly the signed statement, then offers "Save signed PDF" and "Open the receipt page (checks NEAR)". |
| Hosted front | `services/hosted/src/front.ts`, `Dockerfile`, `.dockerignore` | `/receipt/<trade id>` and `/proof/` from the image's `site/proof`, under a policy that names exactly the manifest's RPC endpoints; the web app's policy is unchanged. |

## README snippet

### Verifiable payment receipt

Every paid trade has a receipt that nobody has to take on trust. Open `/receipt/<trade id>` on the Dockside app
(or `receipt.html?trade=<trade id>` on the proof page): your browser reads the NEAR escrow contract and checks,
row by row, that the contract runs the audited build, who the buyer and supplier are, the amount and asset, that
the inspection passed and the release was approved on it, that the ledger still balances, and that the release
transaction paid exactly that amount to the supplier. Green means every check passed; the QR code on the printed
receipt opens the same check on any phone.

From the payout tab, "Prepare signed receipt" gives a one-page PDF signed by the deployment's audit-export key.
Check a saved PDF offline:

```powershell
pnpm run verify-receipt .\dockside-receipt-<trade id>.pdf --trusted-keys .\dockside-audit-export-keys.json
```

It verifies the signature and re-renders the PDF from the signed statement, so any edit to the file is caught.
Try it on testnet: the receipt of trade `trd_197c633d724eeb2cddc64d6dabf55976` verifies 9 of 9 checks live.
