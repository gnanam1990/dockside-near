## What changed

Contract (`contract/crates/`):

- `terms.asset` is `{kind: NEAR_NATIVE, network}` or `{kind: NEP141, network, tokenAccountId, decimals}`, signed
  with the rest of the terms; a successor revision cannot change it.
- A token trade is funded by the funder's own `ft_transfer_call` on the token contract with `msg`
  `{"tradeId", "termsDigest"}`. Only the token the terms name can credit the trade. A refused funding (unknown
  trade, wrong token, wrong digest, over the cap, dust, expired, frozen, malformed) stores nothing and returns the
  whole amount to the sender through the receiver's return value, with the reason in the log.
- Release and refund of a token trade are one `ft_transfer` with a private settlement callback; a failed transfer
  restores the exact reservation or refund bucket, as for native NEAR. A transfer that succeeded is settled as
  transferred whatever it returned.
- `check_payee_storage`: the token contract must report the payout destination as storage-registered before a
  release intent can lock the value for it (and before a destination change can be activated).
- `new(network, min_deposit_yocto, max_trade_amount, nep141_token, min_deposit_nep141)`: `near-testnet` or
  `near-mainnet`; mainnet only with non-zero caps (default 5 NEAR and 25000000 token units, 25 USDC) and, for
  token trades, only for the one pinned token. Nothing can be changed after initialisation.
- A token transfer without a funding message is still an unexpected asset: recorded, never credited, recoverable
  to its proven sender.

run-all (`scripts/testnet-deploy/`): `--asset usdc --token <id>` for all four journeys (paid, hold, refund,
refusal); `--network mainnet` only with `--i-understand-real-funds`; a preflight that checks the chain id, the caps
and the exposure of the run and prints every amount before anything is sent; `--dry-run`. Details:
[scripts/testnet-deploy/README.md](../../scripts/testnet-deploy/README.md), "USDC journeys and the real-funds path".

## Tests added

Core host tests, `contract/crates/dockside-escrow-core/tests/m50_nep141_rail.rs` (15):

- the token and its decimals are bound by the revision digest; the asset schema is exact per kind;
- only the named token contract credits a trade, for the active digest; native NEAR cannot fund a token trade
  and tokens cannot fund a native trade; a refused deposit changes nothing;
- the funding message decides between funding and an unexpected asset;
- the same deposit sequence gives the same ledger for both assets;
- a release cannot lock value for an unregistered payee; a token release settles or rolls back exactly; a hold
  blocks it until the risk principal resolves it;
- token refunds return to the original funder; a failed refund transfer restores the exact bucket;
- a successor revision can never change the asset; a destination change needs the new payee registered first;
- the cap bounds the trade amount and the value a trade holds; a pinned token is the only one accepted;
- the network guard accepts mainnet only with non-zero caps; mainnet terms use their own profile.

near-sdk unit tests of the wrapper, `contract/integration/sandbox-tests/tests/near_sdk_unit.rs` (22 in all, 15 new
and one rewritten): the `new` guard; `ft_on_transfer` funding and every returned refusal with its logged code; the receipts
scheduled for a token release and refund (`ft_transfer`, one yoctoNEAR, exact arguments); the payee check and its
callback; a transfer that succeeded with a long return value is PAID; a failed storage view changes nothing.

near-workspaces tests on nearcore with a real NEP-141 contract,
`contract/integration/sandbox-tests/tests/m50_nep141_rail.rs` (8): paid; hold then paid; mutual-cancel refund with
the excess return; a failed token transfer rolled back exactly (release and refund); cap and pinned token; a
squatted trade id; the trade token without a funding message (recorded, never credited, recovered); the
`near-mainnet` label. After every step the harness compares the contract's views with the host mirror and checks
that the escrow's token balance equals what its ledgers and unexpected-asset records say it holds.

run-all on nearcore, `run_all_on_sandbox.rs`
(`run_all_runs_the_usdc_journeys_and_the_mainnet_label_on_sandbox`): the four journeys in the token, the dry run,
the cap, another token, and the mainnet label with and without the flag.

run-all guards, `packages/near/test/m50-run-all-usdc-mainnet.test.ts` (13): network and account rules, asset and
amount flags, the `new` arguments, the exposure check and the value plan.

Two existing tests changed because the behaviour they pinned changed: `t007_t008_funding.rs` (a bare `NEP141` kind
is now malformed, an unknown kind is still `UNSUPPORTED_ASSET`) and the init test in
`packages/near/test/m02-escrow-wasm.test.ts` and `sandbox_escrow.rs` (mainnet is refused without a non-zero cap,
not unconditionally).

## README snippet (for the stage that integrates the README)

```markdown
### USDC and mainnet

The escrow can hold a trade in a NEP-141 token as well as in native NEAR. The token contract and its decimals are
part of the terms both parties sign. The buyer funds with one `ft_transfer_call`; the escrow credits a trade only
when the calling token is the one the terms name and the transfer names the terms digest, and returns anything else
to the sender. Release and refund are one `ft_transfer` each; if the token contract rejects it, the ledger goes back
exactly as it was. A payout cannot be locked for a supplier account the token does not know.

A mainnet deployment is capped at initialisation and the caps cannot be changed: by default 5 NEAR or 25 USDC per
trade, including any excess. It accepts one token contract, fixed at initialisation.

    scripts/testnet-deploy/run-all --network testnet --asset usdc --token <USDC contract> --journey paid

`--network mainnet` runs only with `--i-understand-real-funds`, and `--dry-run` prints every amount and stops before
anything is sent.

Status: built and tested on a local NEAR node with a real token contract. Awaiting an independent audit and the
owner's approval; not deployed.
```

## Owner steps

Nothing here was run. Each is one PowerShell line from the repository root of a checkout of this branch; the owner
signs every transaction from their own keychain.

1. Read [M50-review-packet.md](M50-review-packet.md) and the audit summary; approve or send back.
2. Build the deployable wasm (about 25 minutes, needs Docker):

   ```powershell
   $env:DOCKSIDE_DOCKER="wsl.exe -d Ubuntu-24.04 -u root -- docker"; pnpm run contract:reproduce
   ```

   `.data/repro/build-manifest.json` must show SHA-256 `46f982e44932cc85a8e13c3c15d016b349505279568cd6d74e2ae722ac80e99e`.
3. Create an empty testnet account for the new build (it cannot go over escrow2):

   ```powershell
   near.cmd account create-account sponsor-by-faucet-service gnanam1990-dock-escrow3.testnet autogenerate-new-keypair save-to-keychain network-config testnet create
   ```

4. Register the buyer with testnet USDC, then get test USDC for `gnanam1990-dock-buyer.testnet` from Circle's
   faucet (faucet.circle.com, NEAR Testnet):

   ```powershell
   near.cmd contract call-function as-transaction 3e2210e1184b45b64c8a434c0a7e7b23cc04ea7eb7a6c3c32520d03d4afcb8af storage_deposit json-args '{\"account_id\":\"gnanam1990-dock-buyer.testnet\",\"registration_only\":true}' prepaid-gas '30.0 Tgas' attached-deposit '0.00125 NEAR' sign-as gnanam1990-dock-buyer.testnet network-config testnet sign-with-keychain send
   ```

5. See the plan without sending anything:

   ```powershell
   $env:DOCKSIDE_ESCROW_ACCOUNT="gnanam1990-dock-escrow3.testnet"; $env:DOCKSIDE_BUYER_ACCOUNT="gnanam1990-dock-buyer.testnet"; $env:DOCKSIDE_SUPPLIER_ACCOUNT="gnanam1990-dock-supplier.testnet"; $env:DOCKSIDE_RELAYER_ACCOUNT="gnanam1990-dock-relayer.testnet"; powershell -ExecutionPolicy Bypass -File .\scripts\testnet-deploy\run-all.ps1 --network testnet --asset usdc --token 3e2210e1184b45b64c8a434c0a7e7b23cc04ea7eb7a6c3c32520d03d4afcb8af --dry-run
   ```

6. Deploy and run the paid journey (same line without `--dry-run`). It prints the relayer key file it saved.
7. Hold, refund and refusal journeys on the same deployment: the same line with
   `--skip-deploy --relayer-key-file "<file from step 6>" --journey hold` (then `refund`, then `refusal`).

Mainnet (build plan D2) is the same with mainnet accounts, `--network mainnet --i-understand-real-funds` and the
mainnet token id, and only after the audit and the testnet run. Always `--dry-run` first.
